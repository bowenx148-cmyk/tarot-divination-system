# 待办：用户体系（登录系统）

- **类别**: 新能力（架构级）
- **状态**: ⏸ 远期（2026-09-16 记为远期，不实现）
- **来源**: 决策 [D8](../SPEC.md)（加密边界）与 [D9](../SPEC.md)（试用一次）各自的"远期"部分
- **优先级**: **本文件中优先级最高的一项之一**——它是另外两件事的共同前置

## 为什么 D8 与 D9 合成一份规格

两处"远期"看起来无关，其实**卡在同一件事上**：

| 决策 | 现状 | 远期目标 | 共同前置 |
|---|---|---|---|
| **D8** 加密边界 | 加密在客户端做，**不防 XSS 与会话期扩展读取** | 主密码 PBKDF2 派生；或**服务端托管 Key** | 后者需要**用户体系**（"这个 Key 是谁的"） |
| **D9** 试用一次 | 基于 deviceId（localStorage）+ 服务端记录，**尽力而为**——清 localStorage / 换浏览器 / 无痕可绕过 | 真正的"一人一次" | 需要**用户体系**（"这个人是谁"） |

所以：**先有用户体系，这两件事才谈得上**。分成两份规格会掩盖这个依赖。

## 问题描述

当前没有登录系统，因此：

1. **无法识别"人"**，只能识别"设备"（deviceId）→ 防滥用是尽力而为的（D9）
2. **无法托管用户的 API Key** → 加密只能在客户端做，密钥与密文同处浏览器（D8）

## 目标

引入最小可用的用户体系，使"一人一次"与"服务端托管 Key"成为可能。

## 验收标准

**本条目本身太大，不应一次做完。** 落地时分阶段，每阶段独立验收：

- [ ] **阶段 0 · 决策**：明确"要解决的是防滥用还是 Key 托管，还是两者"——**先只做驱动它的那一半**
- [ ] **阶段 1 · 身份**：用户可注册/登录；服务端能稳定回答"这是谁"
- [ ] **阶段 2 · 归因**：`trial` / `quota` / `rate-limit` 的键从 deviceId 换成 userId
       —— 此时 D9 的"一人一次"才真正成立
- [ ] **阶段 3 · Key 托管**：API Key 存服务端（加密存储），浏览器不再持有明文
       —— 此时 D8 的"客户端解密"边界才被真正移除
- [ ] **隐私**：新增的任何"人"级数据须在 [`../../README.md`](../../README.md) 的隐私边界中如实声明；
      **不得**记录问题内容与单次调用明细（沿用 N3 的聚合口径）

## 技术方案

**尚未设计。** 本文件只固定"要做什么、为什么、验收什么"，不预先规定实现——
真要做时，先把它拆成阶段 0 的子规格（一个阶段一个文件），再动代码。

需要先想清楚的几件事（留给阶段 0）：

- 自建账号 vs 第三方登录——考虑到部署是**公网 IP + HTTP 明文**（[§三](../OPERATIONS.md)），
  OAuth 回调与 Cookie 安全都受限，可能反而推高复杂度
- 阶段 1 与 2 之间，**存量 deviceId 数据如何迁移**（还是直接作废重来）
- 引入用户体系会显著抬高项目的运维面（数据库、会话、密码重置……）——
  **先确认它带来的收益是否值得**。如果目的只是防滥用，IP 限流 + 每日熔断可能已经够用；
  如果目的是 Key 托管，那真正的驱动因素其实是"想让用户不必自备 Key"

## 风险与假设

- **风险（高）**：这是本项目**架构级**的改动，会引入一个此前完全不存在的运维面
  （持久化用户数据、会话管理、密码重置流程）。当前项目是"无状态 + Redis 计数"的简单形态，
  引入用户体系后复杂度会上升一个量级。
- **风险**：HTTPS 缺失（已接受）会放大账号相关的风险——密码/Cookie 明文过网。
  **若要做用户体系，可能必须先解决 HTTPS**，这会把它与 `plan/` 下的另一项关联起来。
- **假设**：现阶段不做是**可接受的**——站点定位是简历演示（HR / 面试官试用），
  不是面向公众的生产服务；现有的尽力而为防滥用已匹配该定位。

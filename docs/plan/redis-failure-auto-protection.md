# 待办：Redis 故障时的自动阻断 / 恢复

- **类别**: 运维健壮性
- **状态**: ⏸ 未开始（2026-09-18 从 OPERATIONS §三 提取）
- **来源**: 原 `OPERATIONS.md` §三「Redis 故障时降级但无自动处置」

## 问题描述

Redis 挂掉时，配额 / 免费试用 / IP 限流会**整套静默降级为单实例内存实现**，
而站点**仍返回 200、看起来一切正常**——只是防滥用全部失效。

现状**已有探测**（UptimeRobot 监控 `/api/health`，该端点在 Redis 连不上时返回 503，
台账 N2/N9），但**探测到之后仍需人工处理**：没有自动恢复、也没有自动阻断。

## 目标

在"Redis 不可用"这个状态下，系统**自己**做出一个明确的选择，而不是无声地降级。

## 验收标准

**先做决策，再谈实现。** 本条目第一阶段要回答的是：

- [ ] **决策**：Redis 不可用时，系统应当——
      **(a) 拒绝服务**（系统 Key 直接不可用，宁可不可用也不失控），还是
      **(b) 继续服务但降级**（现状），还是
      **(c) 视情况**（如：有个人 Key 的用户不受影响，走系统 Key 的拒绝）？

> ⚠️ **不预设答案。** 三种各有代价：(a) 可用性换成本控制；(b) 成本控制换可用性；
> (c) 最合理但最复杂。**这是负责人的业务决策，不是技术决策**——取决于"系统 Key 被刷爆"
> 与"面试官打开是 503"哪个更不能接受。

决策后的实现验收：

- [ ] 选择被写进代码（而非仅存在于文档），且有测试锁定
- [ ] `/api/health` 仍如实反映 Redis 状态（不得因为"降级也算正常"而改成 200）
- [ ] 若选 (a) 或 (c)：降级/拒绝行为有**明确的用户可见提示**，不是静默失败

## 风险与假设

- **风险**：若选 (a) 拒绝服务，则 **Redis 一挂全站不可用**——把一个"静默降级"问题
  换成了"单点故障"问题。当前 UptimeRobot 已有告警，人工介入的延迟是可接受的，
  这可能使 (a) 的收益不足以抵消风险。
- **假设**：当前"人工处理"在站点定位（简历演示、低流量）下是够用的——
  这正是它至今未做的原因。

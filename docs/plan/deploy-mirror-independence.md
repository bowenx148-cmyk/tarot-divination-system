# 待办：摆脱部署链路的镜像单点依赖

- **类别**: 运维健壮性
- **状态**: ⏸ 未开始（2026-09-18 从 OPERATIONS §三 提取）
- **来源**: 原 `OPERATIONS.md` §三「部署链路单点依赖第三方镜像」

## 问题描述

服务器**直连 GitHub 超时**（这正是当初引入镜像的原因）。N11 迁移到 git 部署时，
`origin` 被写死为第三方代理 `ghfast.top`：

```
https://ghfast.top/https://github.com/HammerRoot/indigo-tarot.git
```

于是：**该代理失效 ⇒ `git fetch` 失败 ⇒ 在找到替代镜像前完全无法部署。**

影响面有限——`deploy.sh` 的 `set -euo pipefail` 会让它在 fetch 处安全中断，
**不污染线上**（线上仍是旧版本）。但"无法部署"本身仍是单点。

## 目标

部署链路不再依赖**单一**第三方代理：要么有可切换的备选，要么根本不需要代理。

## 验收标准

- [ ] **决策**：走哪条路——（a）自建/gitee 镜像仓作为 origin；（b）保留镜像但准备好
      一个已验证可用的备选；（c）让服务器能直连 GitHub（换网络出口 / 走代理）
- [ ] 按决策落地后，**在一个"当前 origin 不可用"的场景下实测部署仍能进行**
      （这是本条目的核心验收——不实测等于没做）
- [ ] 恢复路径写进 [`../DEPLOYMENT.md`](../DEPLOYMENT.md) §3.2，且是从未做过此项的人
      照着就能执行的程度

## 技术方案

**待决策。** 已知的候选路径：

| 方案 | 代价 |
|---|---|
| **gitee 镜像仓** | 需维护同步（gitee 的 GitHub 同步有频率限制）；仓库是公开的，可行 |
| **备选代理** | 便宜，但仍是第三方依赖，只是从单点变双点；且需**定期验证**备选仍可用 |
| **服务器换网络出口** | 根治，但涉及服务器网络配置，改动面最大 |

> 现状的恢复动作（`git remote set-url origin <新镜像>/…`）已在
> [`../OPERATIONS.md`](../OPERATIONS.md) §三 记录——但**那是恢复动作，不是方案**。

## TDD 测试计划

**不设自动化测试**：需真实服务器与真实的网络不可达场景。

**验收方式**：制造一次"原 origin 不可用"（如临时指向一个不存在的地址），
确认按文档的恢复步骤能切到备选并**成功拉取一次**，然后切回。

## 风险与假设

- **风险**：做"双镜像"若不定期验证备选，备选会因为无人使用而静默失效——
  等于**付出复杂度却没换来可靠性**。若要选 (b)，必须同时定一个验证节奏。
- **假设**：ghfast.top 至今可用（2026-09-18 实测 clone 成功，236 objects / 29.44 MiB /
  4.59 MiB/s），所以本条目**不是紧急项**。

## 影响范围

- 无应用代码改动
